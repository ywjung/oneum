계획과 달라진 것:
- **액티비티는 NativeActivity, 껍데기는 Java**로 했다(계획은 GameActivity와 Kotlin). 한글 입력은 어느 쪽이든 직접 만든 입력 뷰가 맡으므로 GameActivity의 글자 입력이 필요 없었고, NativeActivity는 AndroidX 라이브러리 없이 Android에 든 클래스만으로 된다. Kotlin 플러그인도 받지 않아도 된다. 대가는 접근성: eframe의 `accesskit`이 NativeActivity에서는 컴파일되지 않아 Android에서만 껐다. 2026-11-22부터는 UI 라이브러리가 만드는 접근성 트리(egui에 늘 들어 있는 AccessKit의 것)를 플러그인이 프레임마다 받아(`platform::android::a11y`) 펼친 뒤(`ui::accessible`) 화면 크기의 빈 Java 뷰(`A11yHost`)에 넘기고, 그 뷰가 노드마다 가상 뷰를 시스템에 보여 준다. TalkBack이 항목 사이를 밀어서 옮기고 두 번 눌러 실행하는 것은 된다(에뮬레이터에서 TalkBack을 켜고, TalkBack이 보내는 요청을 같은 길로 보내 확인). **터치하여 탐색은 안 된다**: TalkBack이 보내는 hover 사건을 winit이 처리하지 않고 삼켜서 Java 뷰에 닿지 않는다. TalkBack의 초점 테두리도 안 보인다(시스템이 앱 창의 뷰 표면에 그리는데, 그 표면은 NativeActivity가 가져갔다).
- **한글 입력**: 액티비티에 보이지 않는 입력 뷰(`InputView`)를 두고, 입력기가 쥐고 있는 글자 전체를 바뀔 때마다 앱에 알린다. 앱은 앞서 받은 것과의 차이(지울 글자 수와 새 글자)를 키 입력으로 바꿔 넣는다(`platform::typed`, 모든 시스템에서 테스트). 화면을 누르면 입력기 상태를 비운다(칸을 버튼으로 지우거나 커서를 옮긴 경우). 사용자가 자판을 내리면 입력 칸도 포커스를 놓는다.
- **에뮬레이터의 Vulkan 드라이버가 객체에 이름을 붙일 때 죽는다**(디버그 빌드에서 wgpu가 붙이는 이름). Android에서는 그 기능을 끈다(`ui::renderer::instance_flags`).
- **기본 출력 장치**: cpal은 Android에서 시스템 기본 출력을 장치 목록에 없는 별도의 장치로 준다. 장치를 ID로 찾던 코드와 "장치가 아직 있는지" 확인하던 코드가 그것을 없는 장치로 봤다(재생이 1초 뒤 멈춤). 기본 장치를 따로 인정하게 고쳤다(`audio::output`).
- **JNI 라이브러리는 0.22**(계획 때 가정한 0.21과 API가 크게 다르다). android-activity가 쓰는 버전에 맞췄다.
- **오디오 포커스는 앱을 열 때가 아니라 재생이 시작될 때** 요청한다(앱을 여는 것만으로 다른 앱의 음악을 멈추지 않게). 재생 상태를 알리는 길(`nowplaying`)에 붙였다.
- **프로세스는 화면과 함께 끝난다.** winit은 한 프로세스에서 창을 한 번만 만들 수 있어서, 액티비티가 없어지면(최근 앱에서 밀어 없앰) 세션을 저장하고 프로세스를 끝낸다. 재생도 거기서 끝난다.
- **폴더 선택기의 제한**: Android의 선택기는 저장소의 맨 위와 Download 폴더 자체를 고르지 못하게 한다(그 안의 폴더는 됨).
- 앱 전용 crate를 따로 두지 않았다. `cargo rustc --crate-type cdylib`로 라이브러리 crate를 Android에서만 공유 라이브러리로 빌드한다(`scripts/android-build.sh`). 다른 판의 빌드는 그대로다.
- `cargo-ndk`는 쓰지 않는다. `scripts/android-env.sh`가 NDK의 컴파일러를 cargo에 알려 준다.

아래는 시작할 때 세운 계획이다.

이 문서에서 "확인함"은 이 저장소의 코드나 이 Mac에 있는 라이브러리 소스·도구를 직접 본 것이다. "확인 필요"는 아직 해 보지 않은 것으로, 대부분 0단계에서 가린다. Android의 권한과 API에 관한 서술은 해 보고 적은 것이 아니므로 0단계에서 다시 확인한다.

## 1. 결론

- **할 수 있다고 본다.** 재생·보관함·저장 코드(약 3.1만 줄)는 화면과 분리되어 있고, 폰 화면(약 5,200줄)은 iPhone용으로 이미 있다. 지금 쓰는 버전의 winit·cpal·eframe에 Android용 코드가 들어 있다(확인함).
- **iPhone 때보다 새로 만들 것이 많다.** iPhone은 Rust만으로 끝났지만 Android는 **Kotlin으로 쓴 얇은 껍데기**가 있어야 한다: 화면을 꺼도 재생을 이어 가는 서비스와 알림, 권한 요청, 글자 입력의 다리.
- **가장 큰 위험은 한글 입력이다.** 지금 쓰는 winit은 Android에서 자판을 띄우기만 하고 조합 중인 글자를 앱에 넘겨주지 않는다(확인함). 다리를 직접 놓아야 하고, 0단계에서 되는지부터 본다.
- **음악 파일을 어디서 읽을지는 배포 범위에 달렸다**(4.1). 본인 기기에 직접 설치하는 것과 Play 스토어에 올리는 것은 쓸 수 있는 권한이 다르다.
- **기간은 0단계 뒤에 추정한다.** 지금 숫자를 적으면 근거 없는 값이 된다.
- **시작 전에 정해 주실 것이 일곱 가지 있다**(7절). 그중 넷은 내려받기라서 허락이 필요하다.

## 2. 화면 방식과 액티비티

### 화면: egui 유지 (권고)

| | A. egui 유지 + iPhone용 폰 화면 (권고) | B. Kotlin(Compose) 화면 + Rust 코어 |
|---|---|---|
| 새로 쓰는 것 | Android 플랫폼 모듈, Kotlin 껍데기, 뒤로 가기·여백 처리 | 화면 전체, Rust↔Kotlin 연결 계층 |
| 다시 쓰는 것 | 폰 화면 전부(`ui/phone`), 테마·위젯·미터·이퀄라이저, 자동 조작 채널 | 코어만 |
| 약점 | 한글 입력 다리가 필요, 스크롤·제스처가 Android 기본과 다른 느낌, TalkBack 확인 필요 | 작업량이 가장 큼, 화면이 세 벌(데스크톱·iPhone·Android)이 됨 |

iPhone에서 A안이 통했고 같은 화면을 그대로 쓸 수 있으므로 A안을 권한다. 0단계에서 한글 입력·그리기·백그라운드 왕복이 통과하지 못하면 B안을 다시 본다.

### 액티비티: GameActivity (권고)

winit은 Android에서 두 가지 액티비티를 지원한다(확인함: `android-native-activity`, `android-game-activity`).

- **NativeActivity**는 Kotlin 없이도 되지만, eframe의 접근성 기능(`accesskit`, 지금 켜져 있음)이 이 방식에서는 컴파일되지 않는다(확인함: eframe이 컴파일 오류를 낸다).
- **GameActivity**는 Gradle 프로젝트와 AndroidX 라이브러리가 필요하다. 서비스와 권한 때문에 Kotlin 껍데기는 어차피 필요하므로 이쪽을 쓴다. 글자 입력의 다리도 이 액티비티를 상속한 클래스에 둔다.

### 의존성

- Android 코드가 있는 것(확인함): winit 0.30.13, cpal 0.18.2(AAudio 백엔드, 장치 목록은 Java의 AudioManager를 JNI로 읽음), eframe·egui-winit 0.37, notify 8(inotify).
- 운영체제와 무관한 것: symphonia, lofty, rubato, rtrb, rusqlite(SQLite를 함께 빌드하므로 NDK의 C 컴파일러가 필요하다).
- Android에서 빼는 것: `rfd`(지금은 "iOS가 아니면"으로 들어가 있어 조건을 고친다), `muda`(이미 macOS 전용).
- 새로 받아야 하는 것: Android용 crate들(`ndk`, `jni`, `android-activity`, 접근성의 Android 부분 등)은 이 Mac에 하나도 받아져 있지 않다(확인함). Gradle 쪽에서는 Android Gradle 플러그인과 AndroidX 라이브러리.
- 그래픽: wgpu는 Android에서 Vulkan이나 OpenGL ES로 그린다. 에뮬레이터와 실제 기기에서 어느 쪽으로 도는지는 확인 필요.

## 4. Android가 요구하는 것

### 4.1 음악 파일과 권한

Android 11부터 앱은 공유 저장소의 파일을 마음대로 읽지 못한다. 스캐너는 파일 경로로 읽으므로(`std::fs`), 고를 수 있는 길은 셋이다.

| | 가. 모든 파일 접근 | 나. 오디오 읽기 권한 | 다. 폴더를 골라 접근(SAF) |
|---|---|---|---|
| 권한 | `MANAGE_EXTERNAL_STORAGE`(설정 화면에서 켬) | `READ_MEDIA_AUDIO`(Android 13+), 그 전은 `READ_EXTERNAL_STORAGE` | 없음(폴더 선택기) |
| 읽을 수 있는 것 | 공유 저장소 전부, SD 카드, USB 저장 장치 | 음악 파일만. 옆에 있는 `.cue`·`.lrc`·표지 그림은 못 읽는다 | 고른 폴더 전부 |
| 코드 | 스캐너 그대로 | 스캐너 그대로. CUE 시트·`.lrc` 가사·폴더 표지가 빠진다 | 경로가 아니라 주소로 읽어야 해서 `library`와 `audio`에 파일 접근 계층을 새로 넣어야 한다(큰 변경) |
| Play 스토어 | 음악 앱에는 허용되지 않을 가능성이 높다 | 문제없음 | 문제없음 |

- **본인 기기에 직접 설치한다면 "가"를 권한다.** 데스크톱처럼 폴더를 추가해 쓰고 CUE·가사·표지가 모두 된다.
- **Play 스토어에 올린다면 "나"로 시작하고**, 빠지는 기능을 감수하거나 "다"를 5단계 이후에 한다.
- **2026-11-22: "나"를 기본으로, "가"를 선택으로 바꿨다.** 첫 화면의 **접근 허용**은 시스템의 "음악 및 오디오" 질문을 띄우고(두 번 거절한 뒤에는 앱 설정 화면), 설정 → 보관함의 **모든 파일 접근 (선택)**이 "가"의 설정 화면을 연다. 에뮬레이터(Android 16)의 MediaStore가 오디오로 보는 것: FLAC · MP3 · M4A(AAC · ALAC) · Ogg · Opus · WAV · AIFF · MP2 · MKA. WavPack · Monkey's Audio · DSD(.dsf · .dff)는 오디오로 보지 않아 "나"만으로는 보이지 않는다. 경로로 읽으므로 "다"의 큰 변경은 하지 않았다.
- **2026-11-24: Google Play용 빌드에는 "가"가 없다.** Google의 정책이 "모든 파일 접근"을 미디어 파일 접근 용도로는 허용하지 않아, 그 선언을 직접 설치용 빌드의 매니페스트로 옮기고(`android/app/src/direct/`) 앱은 선언이 없는 빌드에서 설정의 그 줄을 보여 주지 않는다. Play용 빌드에서 WavPack · Monkey's Audio · DSD 파일은 **음악 파일 열기**로 고른 것만 재생된다(선택기가 그 파일들을 회색으로 보이던 것을 고침). 곡 옆의 표지 · 가사 · CUE를 Play용 빌드에서 읽으려면 "다"가 필요하다 — 하지 않았다([PLAY_STORE.md](PLAY_STORE.md) 3절).
- 어느 쪽이든 앱 자신의 폴더(`Android/data/<패키지>/files`)는 권한 없이 읽고 쓸 수 있다. PC에서 케이블로 넣을 수 있는지는 확인 필요.
- 위 표의 권한 동작은 Android 버전마다 다르다. 0단계에서 에뮬레이터(Android 15·16)로 실제로 읽히는지 확인한다.
- 폴더 감시: 공유 저장소에서는 파일 변경 알림을 믿을 수 없다고 보고 iPhone처럼 앞에 있는 동안 30초마다 다시 스캔한다(`library::watch`의 `POLLED_ONLY`에 Android를 더함).
- 보관 공간 경로: Android는 앱을 업데이트해도 앱 폴더의 경로가 바뀌지 않는 것으로 안다(확인 필요). 바뀌더라도 `Db::follow_home`이 이미 있다.

### 4.2 소리

- 출력은 cpal의 AAudio 백엔드. 스트림은 시스템 믹서를 거치고, 믹서가 장치의 샘플레이트(보통 48kHz)로 바꾼다. 앱의 리샘플러가 먼저 장치 샘플레이트에 맞추므로 지금의 경로가 그대로 통한다.
- **오디오 포커스**: 다른 앱이 소리를 내거나 전화가 오면 포커스를 잃는다. 잃으면 일시정지, 되찾으면(우리가 멈춘 경우에만) 재생 — iPhone의 끊김 처리와 같은 규칙. JNI로 요청하고 알림을 받는다.
- **이어폰 분리**: `ACTION_AUDIO_BECOMING_NOISY` 알림에 일시정지.
- **출력 장치 선택·독점**: 1차에서는 없다.
- **USB DAC 비트퍼펙트**: Android 14부터 USB 장치에 믹서를 거치지 않는 출력을 요청하는 API가 있다고 알고 있다(확인 필요). 5단계에서, 실제 기기와 DAC이 있을 때만 한다.
- 메모리 재생의 상한은 iPhone처럼 따로 둔다.

### 4.3 백그라운드 재생, 잠금 화면

Android는 화면에 없는 앱의 프로세스를 언제든 끝낸다. 음악 앱은 **포그라운드 서비스**(종류: 미디어 재생)를 띄우고 **알림**을 보여야 살아남는다.

- Kotlin으로 서비스 하나를 쓴다: 미디어 세션(곡 정보·표지·재생 상태), 미디어 알림(재생·이전·다음), 이어폰·블루투스 버튼.
- 재생 엔진은 지금처럼 Rust의 재생 스레드다. 서비스는 프로세스를 살려 두고 버튼을 Rust로 넘기는 일만 한다(iPhone의 Now Playing과 같은 자리).
- 알림 권한(Android 13+)을 물어야 한다. 거절해도 재생은 되지만 알림이 보이지 않는다.
- 제조사의 배터리 절약 기능이 서비스를 끝내는 기기가 있다. 에뮬레이터로는 알 수 없다.

### 4.4 시작과 종료

- 시작 지점이 `main`이 아니라 `android_main`이고, 앱은 실행 파일이 아니라 공유 라이브러리(`.so`)로 빌드된다(4.7).
- 화면에서 벗어나면 그리는 표면이 없어지고 돌아오면 다시 만들어진다. eframe이 처리하지만, 여러 번 오가도 죽지 않는지 0단계에서 본다(iPhone에서도 같은 것을 확인했다).
- 화면 회전·어두운 모드·자판 때문에 액티비티가 다시 만들어지지 않게 매니페스트에 적는다.
- 프로세스는 알림 없이 끝날 수 있다. 뒤로 갈 때 설정을 저장한다(iPhone에서 한 것과 같다). 대기열·위치·음량은 재생 스레드가 이미 저장한다.
- **뒤로 가기**: 시스템의 뒤로 버튼·제스처가 있다. winit은 이것을 키 이벤트(`BrowserBack`)로 넘겨준다(확인함). 폰 화면에서 시트 닫기 → 플레이어 닫기 → 앞 화면 → 첫 화면에서는 앱을 뒤로 보내기 순서로 잇는다. iPhone에는 없던 일이다.

### 4.5 글자 입력 (한글)

- winit은 Android에서 `set_ime_allowed`로 자판을 띄우고 내리기만 한다. 조합 중인 글자를 알려 주는 이벤트가 없고, GameActivity의 글자 입력 이벤트도 처리하지 않는다(확인함: winit 0.30.13의 Android 코드).
- 그래서 영문은 키 이벤트로 들어올 수 있어도 **한글은 들어오지 않을 것으로 본다**(확인 필요).
- 대응: Kotlin 쪽에서 입력 연결을 직접 만들어 조합 중인 글자와 확정된 글자를 JNI로 넘기고, 앱이 그것을 egui의 입력 이벤트로 넣는다. 넣는 자리는 이미 있다(`raw_input_hook` — macOS의 편집 메뉴 다리와 자동 조작 채널이 같은 자리로 넣는다).
- 0단계의 통과 기준에 "에뮬레이터의 한글 자판으로 `사랑`을 조합해 검색 칸에 넣는다"를 둔다.

### 4.6 화면

- **여백**: Android 15를 대상으로 하면 앱이 상태 표시줄과 내비게이션 막대 아래까지 그리게 된다고 알고 있다(확인 필요). 여백(시스템 막대, 카메라 구멍, 자판)을 Kotlin에서 받아 `window::safe_area_insets`와 `keyboard_height`로 넘긴다. 앱 쪽은 iPhone과 같은 코드다.
- **글꼴**: 시스템 글꼴 폴더의 한글 글꼴을 읽는다. 어느 파일의 몇 번째 글꼴이 한글인지는 확인 필요. 안 되면 한글 글꼴을 앱에 넣는다(용량이 늘어난다).
- **화면 모드**: winit은 Android에서 시스템의 밝은/어두운 설정을 알려 주지 않는다(확인함: 늘 "모름"을 돌려준다). iPhone에서처럼 직접 읽어 넘긴다(`window::system_is_dark`, JNI).
- **가로 화면·접는 화면**: iPhone에서 넣은 가로 배치가 그대로 통한다. 이 Mac에 접는 기기 에뮬레이터가 있다.
- **접근성(TalkBack)**: accesskit에 Android 부분이 있다고 알고 있다(확인 필요).

### 4.7 빌드와 묶기

- Rust 대상: `aarch64-linux-android`. Apple Silicon의 에뮬레이터도 arm64이므로 하나로 실제 기기와 에뮬레이터를 모두 덮는다.
- **앱 전용 crate를 따로 둔다**(`android/` 아래, 공유 라이브러리로 빌드). 지금 crate의 종류를 바꾸면 macOS·Windows·iPhone 빌드에 영향이 가므로, 얇은 crate가 `oneum` 라이브러리를 불러 `android_main`에서 시작한다.
- `cargo-ndk`로 `.so`를 만들고, Gradle 프로젝트(`android/`)가 Kotlin 껍데기와 함께 APK로 묶는다. iPhone의 Xcode 프로젝트에 해당한다.
- 스크립트: `scripts/android-emu.sh`(에뮬레이터에 설치·실행), `scripts/android-device.sh`(실제 기기), `scripts/dev/smoke-android.sh`.
- 서명: 디버그 키로는 본인 기기에 바로 설치된다. 배포용 키는 사용자가 만들어 보관하며 저장소에 넣지 않는다.
- 최소 Android 버전은 0단계에서 의존성이 요구하는 값을 확인해 정한다(AAudio는 Android 8.0부터).

### 4.8 빠지거나 달라지는 것

- 없음(1차): 메뉴 막대, 출력 장치 선택, 독점 출력, 곡의 샘플레이트로 출력, Finder에서 보기, 외장 키보드 단축키.
- 달라짐: 뒤로 가기 버튼, 음악 폴더의 위치(4.1), 알림의 재생 제어, 권한을 묻는 화면.
- iPhone에만 있던 것: "폴더 연결"의 북마크. "가"를 고르면 Android에서는 데스크톱처럼 폴더를 그냥 추가한다.

## 5. 단계

단계마다 `scripts/check.sh`(macOS·Windows·iPhone 린트와 테스트)와 두 스모크 테스트를 돌려 다른 판이 깨지지 않았는지 본다.

| 단계 | 목표 | 하는 일 | 통과 기준 |
|---|---|---|---|
| 0 기술 검증 | A안이 Android에서 되는지 | NDK·Rust 대상·cargo-ndk 설치. 버릴 브랜치에서 최소 앱(GameActivity, egui 목록과 입력 칸, cpal 출력, SQLite, 디코딩 한 곡) | 에뮬레이터에서 화면 전체에 그려짐, 한글 조합 입력, 한글 글꼴, 터치 스크롤, 앞뒤 20회 왕복, 4.1의 권한으로 실제로 파일이 읽힘 |
| 1 코어 빌드 | 화면 없이 Android로 컴파일 | `Cargo.toml` 대상 분리, `platform::android`(중립 대역 위주), 앱 전용 crate, Android 린트를 `check.sh`에 | Android 대상 clippy 통과, 다른 세 판의 검사 통과 |
| 2 소리 내기 | 폰에서 한 곡을 끝까지, 화면을 꺼도 | Gradle 프로젝트, 음악 폴더와 권한, 스캔, 재생, 포그라운드 서비스와 알림, 다시 실행 시 복원 | 에뮬레이터에서 재생(앱 음량 0, 미터로 확인), 화면을 끄고 다음 곡으로 넘어감 |
| 3 폰 화면 | 일상 사용 | `PHONE`을 Android에서 켬, 여백, 자판 높이, 뒤로 가기, 글꼴, 한글 입력 다리, 스크립트 채널 | 스모크 테스트(iPhone의 69항목에 해당하는 것)가 에뮬레이터에서 통과 |
| 4 Android 동작 | 끊김과 생명주기 | 오디오 포커스, 이어폰 분리, 전화, 알림·이어폰 버튼, 권한 거절 때의 안내, 문서 선택기, "OnEum으로 열기", 메모리 상한 | 에뮬레이터로 낼 수 있는 상황(전화 걸려 옴 등)은 확인, 나머지는 미확인으로 적음 |
| 5 확장 | 필요한 것만 | USB DAC(Android 14+), SD 카드·USB 저장 장치, 폴더를 골라 접근(SAF), 태블릿 배치, 외장 키보드 | 기능마다 따로 정함 |
| 6 기기와 배포 | 실제 기기에 설치 | 서명, 아이콘, 오픈 소스 고지에 Android crate 더하기, 사용 안내(한/영), CI, (선택) Play 스토어 | 실제 기기에서 설치·재생·알림 제어 |

1차 목표는 0~4단계다.

## 6. 검증과 위험

### 검증 방법

- **코어**: 지금의 565개 테스트는 운영체제와 무관하므로 Mac에서 계속 돈다.
- **화면**: 에뮬레이터에 `adb`로 설치·실행하고, iPhone 때와 같은 스크립트 채널(명령 파일을 읽어 조작하고 상태를 덤프)을 쓴다. 명령 파일을 앱이 읽을 수 있는 곳에 `adb`로 넣을 수 있는지는 확인 필요. 화면 캡처와 실제 터치는 `adb`로 된다.
- **소리**: 지금처럼 앱 음량 0에서 미터 값과 언더런 수로 확인한다. 에뮬레이터의 소리는 Mac의 출력으로 나오므로 음량 0을 지킨다.
- **이 Mac에 있는 것**(확인함): Android Studio, SDK(플랫폼 33·34·35, 빌드 도구, `adb`, 에뮬레이터), 시스템 이미지 Android 15·16(arm64), 에뮬레이터 두 대(보통 크기 폰, 접는 폰), Java 24, Gradle 9.7.1.
- **없는 것**(확인함): NDK, Rust의 Android 대상, `cargo-ndk`, SDK의 명령줄 도구.

### 에뮬레이터로 확인할 수 없는 것

실제 블루투스·이어폰 분리, USB DAC, 제조사의 배터리 절약이 서비스를 끝내는지, 실제 메모리 한도, 배터리 사용량, 케이블로 파일을 넣는 과정, 손가락으로 끄는 감각. 실제 기기가 있어야 하고, 그때까지는 "미확인"으로 적는다.

### 위험

| 위험 | 대응 |
|---|---|
| 한글 조합 입력이 안 됨 | 0단계에서 다리를 먼저 만들어 확인. 안 되면 검색 칸만 Android의 입력란을 겹쳐 쓰거나 B안 |
| 권한으로 파일이 기대만큼 읽히지 않음 | 0단계에서 4.1의 세 방식을 에뮬레이터에서 실제로 읽어 보고 정함 |
| 에뮬레이터에서 wgpu가 그리지 못함 | 0단계에서 확인. OpenGL ES로 바꿔 보고, 안 되면 실제 기기가 필요 |
| 백그라운드에서 프로세스가 끝남 | 포그라운드 서비스(2단계), 화면을 끈 채 여러 곡을 넘기는 확인 |
| 표면이 없어졌다 생길 때 종료 | 0단계에서 20회 왕복 |
| JNI 코드의 실수로 앱이 죽음 | JNI 호출을 `platform::android` 한곳에 모으고, 예외를 검사하는 얇은 계층을 둠 |
| Kotlin 코드가 늘어남 | 껍데기는 서비스·권한·입력 다리·여백 전달로 한정. 화면과 동작은 Rust에 둠 |
| macOS·Windows·iPhone 빌드가 영향받음 | 앱 전용 crate로 분리, 단계마다 `check.sh`와 스모크 테스트 |
| 실제 기기 없이 끝냄 | 문서에 미확인 항목으로 남기고 "완료"라고 쓰지 않음 |

## 7. 시작 전에 정해 주실 것

1. **내려받기 허락.** (1) Android NDK(용량이 크다. 설치할 때 표시되는 크기를 먼저 알려 드린다), (2) `rustup target add aarch64-linux-android`, (3) `cargo-ndk`, (4) Android용 crate와 Gradle이 받는 라이브러리. 허락하시면 0단계에서 실행한다.
2. **실제 Android 기기가 있는지.** 있다면 기종과 Android 버전. 없으면 에뮬레이터까지만 확인하고 그렇게 적는다.
3. **배포 범위.** 본인 기기에 직접 설치 / Play 스토어. 4.1의 선택이 여기에 달렸다.
4. **음악 파일을 읽는 방식**(4.1의 가·나·다). 본인 기기용이면 "가"를 권한다.
5. **최소 Android 버전.** 정해 둔 것이 없으면 0단계에서 의존성이 요구하는 값을 보고 제안한다.
6. **1차 범위.** 0~4단계로 충분한지, USB DAC이 처음부터 필요한지.
