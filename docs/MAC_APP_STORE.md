# Mac: Mac App Store 배포 준비

작성 2026-11-24 · 대상은 Mac 앱입니다. iPhone 앱의 절차는 [APP_STORE.md](APP_STORE.md), 내려받는 Mac 앱(Developer ID · 공증)은 [RELEASE.md](RELEASE.md) 4 · 5절에 있습니다.

Mac 앱은 이제 두 가지로 나갑니다. **프로그램은 하나**이고 포장과 서명만 다릅니다.

| | 내려받는 앱 (dmg) | Mac App Store의 앱 (pkg) |
|---|---|---|
| 만드는 법 | `scripts/package.sh --dmg --notarize` | `scripts/package.sh --app-store` |
| 서명 | Developer ID + 공증 | Apple Distribution + 스토어 프로파일, 설치 패키지는 설치용 인증서 |
| App Sandbox | 없음 | **있음** (`assets/OnEum.entitlements`) |
| 읽을 수 있는 폴더 | 사용자가 읽을 수 있는 모든 폴더 | 사용자가 앱에 넘겨준 폴더와 파일만 |
| 데이터 위치 | `~/Library/Application Support/OnEum` | `~/Library/Containers/app.oneum.OnEum/Data/Library/Application Support/OnEum` |

표시: **[인증]** Apple 계정 로그인이 필요, **[결정]** 정해야 진행, **[동의]** 약관 동의. 이 단계들은 계정을 가진 사람이 직접 합니다.

## 1. 준비된 것

- **샌드박스 안에서 도는 앱.** 샌드박스의 앱은 자기 컨테이너와 사용자가 넘겨준 것만 읽을 수 있고, 그 권한은 앱을 끄면 사라집니다. 그래서 넘겨받을 때 권한을 담은 책갈피(security-scoped bookmark)를 만들어 데이터 폴더의 `linked-folders.json`에 두고, 다음 실행 때 되살립니다(`src/platform/macos/files.rs`). 샌드박스 밖(내려받는 앱)에서는 이 코드가 아무것도 하지 않습니다.
  - 넘겨받는 길 세 가지: 열기 창에서 고름, 창에 끌어다 놓음, Finder에서 엶(Dock 아이콘에 놓기 포함).
  - 폴더는 수에 제한 없이, 낱개로 연 파일은 최근 1,000개까지 기억합니다. 폴더를 기억하면 그 안의 낱개 파일 기억은 지웁니다.
  - 보관함에서 폴더를 빼면 책갈피를 지우고 권한을 돌려줍니다.
  - 옮겨진 폴더는 새 자리로 따라갑니다. 뽑혀 있는 저장 장치의 폴더는 꽂은 뒤 **다시 읽기**를 누르면 읽습니다.
  - 책갈피를 만들지 못한 것은 이번 실행에서만 읽고, 화면에 알립니다(다시 시도 버튼).
- **권한 파일** `assets/OnEum.entitlements`: 샌드박스, 사용자가 고른 파일 읽기 · 쓰기, 책갈피, 네트워크 나가기, 네트워크 듣기. 각각의 이유는 파일의 주석과 아래 4절에 있습니다.
- **개인정보 매니페스트** `assets/PrivacyInfo.xcprivacy`(추적 없음, 수집 없음), `Info.plist`의 암호화 선언(`ITSAppUsesNonExemptEncryption = false`).
- **패키징**: `scripts/package.sh --app-store`가 샌드박스 앱을 만들고, `scripts/mac-app-store.sh`가 Xcode에 로그인된 계정으로 스토어용 서명을 하게 한 뒤 설치 패키지를 검사합니다. 인증서와 프로파일은 Xcode가 만들고 Apple에 둡니다(키체인에 넣는 것 없음).
- 웹 주소를 여는 방법을 `/usr/bin/open` 실행에서 시스템(NSWorkspace)에 맡기는 것으로 바꿨습니다. 앱이 띄운 프로세스는 앱의 샌드박스에 갇히기 때문입니다. 내려받는 앱도 이 길을 씁니다.

## 2. 만들기

필요한 것은 Developer ID 서명과 같습니다([RELEASE.md](RELEASE.md) 4절 "가"): Xcode ▸ Settings ▸ Accounts에 로그인된 계정, 본인 팀의 ID, **잠기지 않은 화면**.

```bash
ONEUM_MAC_TEAM=<팀 ID> scripts/package.sh --app-store
```

결과물: `dist/mas/OnEum-<버전>-<빌드>.pkg`와 `dist/mas/OnEum.app`. `dist/OnEum.app`(내려받는 앱)은 건드리지 않습니다.

- `dist/mas/OnEum.app`은 **임시(ad-hoc) 서명의 샌드박스 앱**이라 이 Mac에서 바로 열어 볼 수 있습니다. 서명만 하지 않고 이것만 만들려면 `scripts/package.sh --sandbox`.
- 패키지 안의 앱은 스토어용 서명이라 **이 Mac에서 직접 열 수 없습니다**(스토어 프로파일은 기기를 지정하지 않습니다). 설치해서 보는 길은 TestFlight입니다.
- 스크립트의 검사 12항목: 패키지의 설치용 인증서, 앱의 서명과 배포 인증서, 팀, 샌드박스와 권한이 권한 파일과 정확히 같음(디버그 허용 없음), 스토어 프로파일, 검증 채널 없음, 버전 · 빌드, `Info.plist`의 분류 · 최소 macOS · 암호화 선언, 개인정보 매니페스트와 라이선스, **공개되지 않은 창 서버 함수(`CGS…`)를 부르지 않음**(2026-11-26에 더함, 3절의 반려), 홈 경로 없음.
- 있는 패키지만 검사: `scripts/mac-app-store.sh --check dist/mas/OnEum-<버전>-<빌드>.pkg`

## 3. 올리기 — [인증] [결정]

올리기 전에 App Store Connect에서 할 일(본인):

1. **앱에 macOS를 더합니다.** iPhone 앱과 식별자(`app.oneum.OnEum`)가 같으므로, 이미 있는 앱 레코드에 플랫폼으로 macOS를 추가하면 한 번 사면 두 곳에서 쓰는 앱(범용 구입)이 됩니다. 따로 팔고 싶으면 다른 식별자로 새 앱을 만들어야 하고, 그때는 `assets/Info.plist.in`의 식별자를 바꿔야 합니다. **[결정]**
   - **2026-11-24에 추가했습니다**(사용자의 말 "macOS 플랫폼 추가해줘"): 앱 페이지의 버전 메뉴 ▸ **플랫폼 추가** ▸ macOS. "macOS 앱 버전 1.0, 제출 준비 중"이 생겼습니다. 제출하기 전이라면 버전 메뉴에서 지울 수 있습니다.
   - 생긴 버전의 번호는 1.0입니다. 빌드를 붙이려면 **버전** 칸을 빌드의 버전(0.1.0)과 같게 고쳐야 합니다(iPhone 때와 같음). 같은 날 0.1.0으로 고쳐 저장했습니다.
   - 추가된 macOS 버전에는 iPhone 버전의 프로모션 텍스트, 키워드, 지원 · 마케팅 주소, 저작권, 심사 연락처와 메모가 **옮겨져 있었습니다**. 설명은 비어 있었고, 출시 방법은 "자동으로 버전 출시"로 되어 있었습니다(iPhone 버전은 수동). 심사 메모는 iPhone 앱의 것이었습니다.
   - 같은 날 사용자의 말("채워줘")로 채웠습니다: 한국어 · 영어 설명과 심사 메모를 [APP_STORE_LISTING.md](APP_STORE_LISTING.md) "Mac"의 글 그대로(저장 뒤 다시 읽어 해시로 대조), 출시 방법을 수동으로, 빌드 0.1.0 (174)를 버전에 붙임. 심사에 내지 않았습니다.
   - 스크린샷은 `scripts/dev/mac-store-shots.sh`로 만듭니다(두 언어 여섯 장씩, 2560×1600, `dist/appstore/mac`). 2026-11-24에 만들어 같은 날 사용자의 말("넣어줘")로 App Store Connect의 macOS 버전에 넣었습니다: 한국어 여섯 장, 영어(미국) 여섯 장(페이지를 새로 열어 두 언어 모두 "10개 중 6개"로 남아 있는 것을 확인). 앱 안의 브라우저 창에는 파일 올리기가 없어 Chrome 확장으로 올렸습니다. 올릴 때 나오는 안내("이 그림을 모든 Mac 화면 크기와 현지화에 씁니다")는 확인만 누르면 됩니다.
2. 그다음에 올립니다.

```bash
ONEUM_MAC_TEAM=<팀 ID> scripts/package.sh --app-store --upload
```

- 같은 버전에서 빌드 번호는 플랫폼마다 한 번만 받습니다. 빌드 번호는 커밋 수라서, 같은 커밋을 다시 올리려면 커밋이 하나 더 있어야 합니다.
- **2026-11-24에 올렸습니다**(사용자의 말 "올려줘"): 0.1.0 (174). 검사 11항목 통과 뒤 Xcode가 보냈고(`Uploaded OnEum`), 몇 분 뒤 App Store Connect의 TestFlight ▸ macOS 빌드에 "제출 준비 완료, 90일 후 만료"로 나왔습니다. Apple silicon 전용 앱이 받아들여졌습니다. dSYM이 없다는 경고가 하나 나옵니다(만들지 않으므로 매번 나옴).
- **2026-11-24에 심사에 냈습니다**(사용자의 말 "macOS 앱 버전 0.1.0 심사 진행해줘"): **심사에 추가** ▸ **심사를 위해 제출**(그 창에 더 동의할 것은 없었음) → "1개의 항목 제출됨", 상태 "심사 대기 중". Apple은 최대 48시간이 걸릴 수 있고 끝나면 이메일을 보낸다고 합니다. 출시는 수동이라, 승인 뒤 버전 페이지에서 직접 출시해야 합니다. **TestFlight로 받은 앱을 써 보지 않은 채 냈습니다**: 5절의 "확인하지 못한 것"이 그대로 남아 있습니다.
- **2026-11-26에 돌아왔습니다**(상태 "심사를 통과하지 못함", 앱 심사 ▸ macOS 제출의 메시지 한 통, 둘 다 "자동으로 보낸 메시지"). 사람이 앱을 써 보고 짚은 것은 없습니다.
  - **지침 2.5.1, 공개되지 않은 API**: 프로그램이 `_CGSSetWindowBackgroundBlurRadius`를 가리킨다는 것. 창 라이브러리 winit이 창 배경을 흐리게 하는 기능(`set_blur`)에 쓰려고 선언해 둔 함수이고, OnEum은 그 기능을 부른 적이 없습니다. 선언만으로 이름이 프로그램에 들어갑니다(`nm -u`로 보면 `_CGSMainConnectionID`와 함께 나옴). **고침**: winit 0.30.13의 소스를 `vendor/winit`에 두고 그 두 선언과 호출을 뺐습니다(`Cargo.toml`의 `[patch.crates-io]`, 이유는 `vendor/winit/README-ONEUM.md`). 화면은 달라지지 않습니다. 스토어 패키지의 검사에 이 항목을 더했고, 돌아온 패키지(174)로 돌리면 이 항목에서 실패합니다.
  - **지침 2.4.5, `com.apple.security.network.server` 권한에 맞는 기능이 보이지 않음**: 필요 없으면 빼고, 필요하면 이 메시지에 회신해 쓰임을 설명하고 심사 메모에도 적으라는 내용입니다. **권한은 필요합니다**(미디어 서버 찾기: 5절). 같은 날 샌드박스 안의 작은 시험 프로그램으로 다시 확인했습니다: 나가기 권한만으로는 UDP 소켓에 주소를 주는 것(`bind`)도, 주소를 주지 않은 소켓에서 답을 읽는 것(`recvfrom`)도 `Operation not permitted`이고, 한 상대에 연결한 소켓만 그 상대의 답을 받습니다. 서버 찾기의 답은 미리 알 수 없는 서버들이 보내므로 연결한 소켓으로는 받을 수 없습니다. **권한은 그대로 두고**, 심사 메모의 그 줄을 자세히 고쳐 쓰고 회신할 글을 썼습니다([APP_STORE_LISTING.md](APP_STORE_LISTING.md) "Mac"의 `mac.review-notes`, `mac.review-reply`). 이 설명이 받아들여지지 않으면 남는 길은 스토어의 앱에서 서버 자동 찾기를 빼는 것입니다(주소로 추가도 같은 소켓을 쓰므로 그쪽은 연결한 소켓으로 바꿔야 합니다).
  - 다시 내는 순서: 새 빌드를 올리고(빌드 번호는 커밋 수라 자동으로 오름), macOS 버전 페이지에서 빌드를 바꿔 붙이고, 심사 메모를 바꿔 저장하고, 메시지에 회신하고, 버전 페이지 위의 **심사 업데이트**를 누른 뒤(누르기 전에는 다음 단추가 꺼져 있음) 제출 화면에서 **앱 심사에 다시 제출**. 메시지와 **앱 심사에 회신** 단추는 App Store Connect를 넓은 창으로 볼 때만 제출 항목 아래에 보입니다(좁은 창에서는 상태만 보임).
  - **같은 날 아침에 다시 냈습니다**(사용자의 말 "올리고 다시 제출"): 0.1.0 (196)을 올림(검사 12항목 통과, `Uploaded OnEum`, 몇 분 안에 처리되어 빌드 목록에 나옴) → 버전의 빌드를 174에서 196으로 바꿈 → 심사 메모를 새 글로 바꿔 저장(다시 읽어 해시로 대조, 출시는 수동 그대로) → 메시지에 회신(`mac.review-reply`의 글 그대로, 넣은 글을 해시로 대조한 뒤 보냄: "메시지(2개)") → **심사 업데이트** → 항목이 "심사 준비됨" → **앱 심사에 다시 제출** → 제출과 항목이 **"심사 대기 중"**, 빌드 0.1.0 (196). 확인 창이나 동의는 없었습니다. 결과는 아직 보지 못했습니다.
- **2026-11-26 오후, 심사 대기 중이던 0.1.0 (196)을 꺼내 0.2.0 (213)으로 바꿔 다시 냈습니다**(사용자의 말 "최종버전 빌드하고 아이폰과 macos 용 스토어에 배포해줘", 물어서 받은 답 "새 빌드로 바꿔 제출"). Mac의 첫 출시가 0.2.0이 됩니다.
  - 올리기: `ONEUM_MAC_TEAM=<팀 ID> scripts/package.sh --app-store`(검사 12항목 통과, `dist/mas/OnEum-0.2.0-213.pkg`) 뒤 `scripts/mac-app-store.sh dist/mas/OnEum.app --upload`(`Uploaded OnEum`). 올리기 전에 임시 서명의 샌드박스 앱(`dist/mas/OnEum.app`, 릴리스 빌드)을 열어 7초 동안 떠 있는 것을 보았습니다.
  - 심사에서 꺼내기: **앱 심사** ▸ macOS 제출 ▸ 맨 아래 **제출 취소** ▸ 확인("모든 항목을 다시 제출해야 합니다"). 버전의 상태가 "개발자가 취소함"이 되고, 제출 목록에는 "삭제됨"으로 남습니다. Apple과 주고받은 메시지는 그 제출에 남습니다.
  - 버전 페이지: 빌드 줄의 삭제 단추로 196을 떼고, **버전** 칸을 0.2.0으로 고쳐 저장(상태 "0.2.0 제출 준비 중"), **빌드 추가**에서 0.2.0 (213)을 골라 저장. 설명 · 심사 메모 · 스크린샷 · 수동 출시는 그대로였습니다(첫 버전이라 "새로운 기능" 칸은 없음).
  - 저장 직후에는 **심사에 추가**가 꺼져 있었습니다. 페이지를 다시 열자 켜졌습니다. **심사에 추가** ▸ **심사를 위해 제출** → "1개의 항목 제출됨", "심사 대기 중".
  - 심사 결과는 아직 모릅니다. 권한에 대한 설명은 심사 메모에 그대로 있습니다(앞 제출의 회신은 새 제출에 따라오지 않습니다).
  - **같은 날 출시 방식을 자동으로 바꿨습니다**(사용자의 말 "IOS와 macOS 모두 출시해줘", 물어서 받은 답 "승인되면 자동 출시로 바꿈"): 심사 대기 중인 버전 페이지에서 **자동으로 버전 출시**를 골라 저장. 심사를 통과하는 대로 Mac App Store에 나갑니다. Mac용 TestFlight 빌드를 써 본 사람은 여전히 없습니다.
- 반려되면: 고치고, 새 빌드를 올리고(커밋이 하나 이상 더 있어야 빌드 번호가 오릅니다), 버전에 붙여 다시 냅니다. 심사 대기 중인 버전에 새 빌드를 붙이려면 먼저 심사에서 빼야 합니다.
- 올라간 빌드는 Apple의 처리가 끝나면 TestFlight에 나옵니다. **Mac용 TestFlight로 설치해 실제로 써 보는 것이 이 앱의 첫 실사용 확인입니다**(5절).

## 4. 심사에 적을 것 (초안)

샌드박스 권한마다 이유를 묻습니다. 심사 메모에 넣을 내용(App Store Connect에 넣은 영어 글은 [APP_STORE_LISTING.md](APP_STORE_LISTING.md) "Mac"에 있습니다):

- **사용자가 고른 파일 읽기 · 쓰기**: 음악 폴더와 파일을 읽어 재생합니다. 음악 파일은 바꾸지 않습니다. 쓰는 것은 사용자가 저장 창에서 위치를 정한 것뿐입니다(플레이리스트 내보내기, 데이터 내보내기, 로그 저장).
- **책갈피**: 고른 음악 폴더를 다음 실행에도 읽기 위해서입니다.
- **네트워크 나가기**: 같은 네트워크의 미디어 서버(DLNA) 탐색과 재생, 사용자가 등록한 네트워크 폴더(WebDAV), 사용자가 켰을 때만 가사 검색(LRCLIB). 계정도 분석 도구도 없습니다.
- **네트워크 듣기**: 미디어 서버 찾기에만 씁니다. 앱이 자기 UDP 소켓에서 "누가 있나요"를 보내고 그 소켓으로 답을 받는데, 샌드박스에서는 이 권한이 있어야 소켓에 주소가 주어지고 답을 읽을 수 있습니다. 앱은 다른 것을 듣지 않고 아무것도 제공하지 않습니다. **Apple의 자동 검사가 이 권한을 묻습니다**(2026-11-26, 3절): 메모에는 어느 화면에서 쓰는지, 무엇을 보내고 받는지, 권한이 없으면 무엇이 실패하는지를 적습니다.
- 심사하는 사람이 음악 없이 여는 경우: 빈 보관함 화면에서 **폴더 추가**를 누르고 음악 폴더를 고르면 됩니다. iPhone 앱과 달리 샘플 음악은 들어 있지 않습니다.

키워드, 프로모션 텍스트, 개인정보 답변, 처리방침 주소, 수출 규정은 iPhone 앱의 것을 그대로 씁니다. 설명은 Mac의 것을 따로 썼습니다([APP_STORE_LISTING.md](APP_STORE_LISTING.md) "Mac": 샌드박스에서 확인하지 못한 문장의 표가 있으니 TestFlight로 본 뒤 되지 않는 것은 빼세요). Mac용 스크린샷은 따로 필요합니다. App Store Connect의 macOS 버전 페이지가 받는 크기는 2880 × 1800, 2560 × 1600, 1440 × 900, 1280 × 800px이고 10장까지입니다(2026-11-24에 그 페이지에서 읽음). 같은 페이지에 "앱 Sandbox 정보"(샌드박스 권한을 고르는 칸, 선택 사항)가 있습니다. macOS 버전의 정보(설명, 키워드, 주소, 저작권, 심사 정보, 출시 방법)는 iPhone 버전과 따로이고, 추가한 직후의 상태는 3절에 적었습니다.

## 5. 확인한 것과 확인하지 못한 것 (2026-11-24)

확인한 것 — 샌드박스를 켠 시험용 앱(디버그 빌드, 식별자만 다르게, 볼륨 0)으로:

- 앱이 샌드박스 안에서 시작하고 자기 컨테이너를 만듦.
- **넘겨받지 않은 폴더는 읽지 못함**(추가는 되지만 0곡, 책갈피도 만들어지지 않음).
- **Finder가 넘기듯 넘긴 폴더**(`open -a`)는 읽음: 20곡, 책갈피 저장.
- **껐다 켠 뒤에도 그 폴더를 읽고 재생함**(시작할 때 책갈피로 권한을 되살림).
- 낱개로 넘긴 파일 하나도 같음: 재생, 책갈피 저장, 껐다 켠 뒤 재생.
- **보관함에서 폴더를 빼면** 책갈피가 지워지고 권한도 돌려줌(같은 실행에서 그 폴더를 다시 읽으려 하면 0파일).
- 대조: 책갈피 파일을 치우고 켜면 같은 폴더를 읽지 못하고(0파일, "파일을 읽을 수 없어 건너뛰었습니다"), 보관함의 곡은 지워지지 않음. 되돌리면 다시 읽고 재생.
- 소리가 출력 장치로 나감(끊김 0).
- 미디어 서버: 주소로 추가(HTTP), 호스트로 찾기(UDP 검색). 검색은 "네트워크 듣기" 권한이 없으면 `Operation not permitted`로 끝났고, 넣은 뒤 됨. 2026-11-26에 따로 확인: 나가기 권한만 가진 샌드박스 프로그램에서 UDP 소켓은 `bind`가 거절되고, `bind` 없이 보낸 뒤 `recvfrom`도 거절되며, 한 상대에 `connect`한 소켓만 그 상대의 답을 받음(macOS 27.2, 127.0.0.1의 되받아치는 서버로).
- 키체인: 넣고 읽고 바꾸고 지우기.
- 패키지: Xcode가 스토어용 서명과 설치 패키지를 만들고 검사 11항목 통과. 검사가 틀린 것을 잡는지도 확인(서명 없는 패키지, 내려받는 앱으로 만든 패키지, 다른 팀). 스크립트가 거절하는 쓰임(팀 없음, `--dmg`와 함께, 디버그, 샌드박스 밖의 앱, 잠긴 화면)도 확인.
- 고친 뒤 Developer ID 서명(공증 없이)이 전과 같이 됨.

확인하지 못한 것:

- **열기 창에서 고른 폴더와 창에 끌어다 놓은 것**의 권한 저장. 창을 사람이 다뤄야 합니다. 코드는 Finder로 넘긴 것과 같은 함수를 지나갑니다.
- **샌드박스에서 독점 출력과 샘플레이트 맞춤.** 실제 출력 장치의 설정을 바꾸는 일이라 돌리지 않았습니다.
- 스토어용으로 서명된 앱의 실행(TestFlight가 필요), 릴리스 빌드의 샌드박스 앱 실행(시험은 디버그 빌드로 함).
- 심사. (업로드와 App Store Connect의 처리는 2026-11-24에 확인: 3절.)
- TestFlight로 설치한 스토어 서명 앱의 실제 사용. 빌드는 올라가 있으나 설치해 보지 않았습니다.
- 웹 주소 열기(방법을 바꿈)를 실제로 눌러 본 것.

## 6. 내려받는 앱과 다른 점 (사용자에게 알릴 것)

- 앱이 읽는 것은 사용자가 고른 폴더와 파일뿐입니다. 플레이리스트 파일(M3U)이나 Apple Music 보관함 내보내기가 **고르지 않은 폴더의 곡**을 가리키면 그 곡은 읽지 못합니다. 그 폴더를 음악 폴더로 추가하면 됩니다.
- 낱개로 연 파일 옆의 표지 그림 · 가사 파일은 읽지 못합니다(파일 하나에 대한 권한만 받기 때문). 폴더를 추가하면 읽습니다.
- 내려받는 앱의 보관함과 설정은 넘어오지 않습니다(데이터 위치가 다릅니다). 음악 폴더는 다시 추가해야 합니다.
