Gapless 조건과 한계:
- 보장 범위는 **자연스럽게 다음 곡으로 넘어갈 때**입니다. 사용자가 곡을 바꾸거나 seek하면 짧은 페이드(6ms)가 들어갑니다.
- 무음을 잘라내거나 크로스페이드로 흉내 내지 않습니다. 같은 디코드 스레드가 같은 버퍼에 이어 씁니다.
- 곡의 샘플레이트가 출력 장치와 달라 리샘플링할 때도, **두 곡의 샘플레이트가 같으면** 리샘플러 하나를 이어 써서 연속입니다(44.1→48kHz에서 경계 불연속 없음 확인). 두 곡의 샘플레이트가 서로 다르면 리샘플러를 새로 시작하므로 샘플 단위 연속은 보장하지 않습니다(무음은 넣지 않음).
- 곡 기준 ReplayGain에서는 곡마다 이득이 달라 이어지는 앨범에서 음량 단차가 생길 수 있습니다. 그런 앨범은 앨범 기준을 쓰세요.
- 대기열 끝에서 "전체 반복 + 셔플"로 다시 섞을 때는 새 피드를 시작하므로 짧은 틈이 있습니다.
재생 관련 테스트(`audio_pipeline`, `player_flow`)는 타이밍에 민감하므로 여러 번 연속 실행합니다. 처음 15회는 실패 0이었고, 그 뒤 5회 중 1회 무작위 명령 테스트가 실패해
기존 결함 하나를 더 찾았습니다(셔플+전체 반복이 한 바퀴 돌며 대기열을 다시 섞을 때 화면에 공개되는 대기열 사본이 갱신되지 않음). 고친 뒤 12회 연속 통과했습니다.
새 회귀 테스트 중 7개는 해당 수정을 일시적으로 되돌려 **실제로 실패하는지** 확인했습니다
(셔플 순환 뒤 이전 곡, 고장 곡이 섞인 전체 반복, 미리 열기 실패 뒤 "다음에 재생", 멈춤 감시, 재생 횟수, 대기열 재저장, 셔플 순환 때 공개 대기열).

## 음량 분석을 실제 음악으로 (🖥, 2026-11-13)

## 단축키의 키 입력 (🖥, 2026-11-13)
`menukey`(검증 채널)는 키보드가 보고하는 그대로의 키 이벤트(키 코드와 수식키, 현재 자판 배열의 글자)를 만들어 메뉴 막대의 단축키 처리(`NSMenu performKeyEquivalent:`)에 넘깁니다.
앱이 활성 상태일 때 AppKit이 ⌘ 키 입력에 대해 하는 일과 같은 호출이라, 단축키가 그 키에 제대로 등록되어 있고 명령에 이어져 있는지를 다른 앱이 맨 앞에 있어도 확인할 수 있습니다.

| 키 | 결과 |
|---|---|
| ⌥⌘→ / ⌥⌘← | 재생 위치 1.4초 → 7.3초 → 3.2초 |
| ⌘⇧. | 현재 곡이 끝나면 정지 켜짐 → 다시 누르면 꺼짐(Shift를 누른 마침표는 자판에서 `>`로 보고되지만 맞게 처리됨) |
| ⌘Return / ⌘⇧Return | 선택한 곡이 대기열에 +1, +1 |
| ⌘D · ⌥⌘I · ⌘⇧M | 즐겨찾기에 들어감 · 곡 정보 패널 열림 · 음소거 후 원래 볼륨으로 |
| ⌘→ · ⌘E | 다음 곡 · 이퀄라이저 열림 |
| 대조: ⌘.(Shift 없이), ⌥→(⌘ 없이) | 어떤 메뉴 항목도 받지 않음 |

⌥⌘→, ⌥⌘←, ⌘⇧.와 대조 입력 하나는 스모크 테스트에 넣었습니다. ⌘⇧F(Finder에서 보기)는 Finder 창을 여는 동작이라 돌리지 않았습니다.
남은 구간: 실제 키보드에서 누른 키가 활성 앱의 창을 거쳐 메뉴에 닿는 부분. `oskey`가 그 경로를 타지만 앱이 활성 상태여야 하고, 백그라운드에서 띄운 앱은 macOS가 활성화해 주지 않습니다(덤프의 `app_active`가 false).

## VU 미터 (🖥, 2026-11-12)
직접 합성한 기준 신호(24비트 FLAC 사인파)를 실제 앱에서 재생하고(앱 볼륨 0, eqMac 가상 장치) 바늘 위치를 상태 덤프로 읽었습니다.

| 신호 | 기대 | 측정 |
|---|---|---|
| 최대 진폭 −8dBFS 사인파 | 0 VU | 왼쪽·오른쪽 +0.00 VU |
| 최대 진폭 −18dBFS 사인파 | −10 VU | −10.06 VU |
| 왼쪽 −8dBFS, 오른쪽 그 절반 | 0 / −6 VU | −0.00 / −6.02 VU |
| 풀스케일 사인파 | 바늘이 +3 너머 멈춤쇠에 닿고 PEAK 램프 켜짐 | 양쪽 멈춤쇠, 램프 켜짐 |
| 위 상태에서 일시정지 | 바늘이 쉬는 위치로, 램프 꺼짐 | 1.5초 뒤 위치 0, 램프 꺼짐 |

- 앱 볼륨 0에서 측정했으므로 미터가 볼륨과 무관하게 음악의 레벨을 보여 준다는 것도 함께 확인됩니다.
- 화면은 캡처로 확인했습니다: 어두운 테마와 밝은 테마, 1180×760과 900×600 창, 대기열 패널과 함께 연 상태, 풀스케일에서의 PEAK 램프.
  두 미터가 재생 막대 위에 좌우로 놓이고 양옆에 소스·출력이 표시됩니다. 실제 음악에서의 움직임은 눈으로 보지 않았습니다(⏳).
- 미터가 오른쪽 패널에 있던 빌드의 설정 파일(`"right_panel":"Meter"`)도 그대로 읽힙니다(단위 테스트와 실제 실행으로 확인).
- 덱 높이를 끌어 바꾸는 동작은 자동화하지 않았습니다(⏳). 높이에 따른 미터 배치는 단위 테스트로 확인합니다.
- 바늘이 멈춘 뒤 화면을 다시 그리지 않는지는 단위 테스트(정지 상태로 수렴하면 다시 그리기를 요청하지 않음)로만 확인했습니다.

## 출력 품질 옵션 (🖥, 2026-11-12)
이 절은 **MacBook Pro(내장 스피커: 44.1/48/88.2/96kHz, 32비트 부동소수점)와 eqMac 가상 장치(44.1~768kHz)** 에서 확인했습니다.
위 "검증 환경"의 USB DAC는 이번 확인에 쓰지 못했습니다. 직접 합성한 24비트 FLAC(22.05/44.1/44.1/48/96/192kHz, 각 8초)을
앱에서 실제로 재생하고(앱 볼륨 0), 앱 상태 덤프·로그·`oneum-libtool audio-devices`(앱 바깥에서 본 장치 상태)를 비교했습니다.

| 확인한 것 | 결과 |
|---|---|
| 곡의 샘플레이트로 장치 전환(eqMac) | 44.1 → 48 → 96 → 192 → 44.1kHz(22.05kHz 곡은 2배인 44.1kHz)로 곡마다 전환. 앱 바깥에서 본 장치 샘플레이트와 일치 |
| 같은 샘플레이트 두 곡 | 스트림을 다시 열지 않고 이어짐(16초 분량에 스트림 1개) |
| 샘플레이트가 다른 곡 사이의 틈 | 내장 스피커 약 0.75초, eqMac 약 0.6초(스트림 닫기 → 장치 전환 → 스트림 시작). 장치 전환 자체는 스피커 0.02초, eqMac 0.4초 |
| 독점 출력(eqMac, 내장 스피커) | 재생 중 장치의 독점 소유자가 앱의 PID. 재생은 계속되고 장치 분리로 오인하지 않음 |
| 되돌리기 | 대기열 끝, 재생 도중 종료 모두에서 원래 샘플레이트(스피커 48kHz, eqMac 44.1kHz)로 복원되고 독점 해제 |
| 독점 중 시스템 기본 장치 | 스피커를 독점하는 동안 시스템 기본 출력 조회가 비고, 풀면 스피커로 돌아옴(`audio-probe --exclusive`) |
| 메모리 재생 | 덤프의 `in_memory`가 참, 6곡 연속 재생에서 underrun 0 |
| 반복 재열기 없음 | 장치 전환 한 번에 스트림 열기 한 번(로그). 늦게 오는 샘플레이트 알림으로 다시 열리지 않음 |
| 설정·곡 정보 화면 | 재생 탭의 "출력 품질" 스위치 3개, 곡 정보의 `출력 eqMac · 48,000 Hz · 32 bit float · 독점`, `처리 앱 볼륨 (메모리에서 재생)` 확인(화면 캡처) |

찾아서 고친 것: 처음 구현은 하드웨어 포맷 설정으로 샘플레이트까지 바꾸려 했는데, eqMac이 그 요청을 받아 놓고 따르지 않아
전환마다 3초를 기다렸습니다(곡 사이 3.5초 공백으로 측정됨). 샘플레이트를 먼저 바꾸고 비트 깊이는 더 넓은 포맷이 있을 때만 따로
요청하도록 바꾼 뒤 위 수치가 됐습니다.

장치에서 직접 확인하려면:
```bash
cargo run --bin oneum-libtool -- audio-devices
```
```bash
cargo run --bin oneum-libtool -- audio-probe coreaudio:BuiltInSpeakerDevice 44100
```
두 번째 명령은 장치를 1초 동안 그 샘플레이트로 바꿨다가 되돌리며 걸린 시간을 보여 줍니다(소리는 내지 않음. `--exclusive`를 붙이면 그 1초 동안 독점).
```bash
cargo run --bin oneum-libtool -- audio-selftest coreaudio:BuiltInSpeakerDevice
```
세 번째 명령은 볼륨 0으로 재생하면서 "장치 포맷 알림이 늦게 온 상황"을 일으켜 엔진이 재생을 이어 가는지 확인합니다(PASS/FAIL).

**eqMac 가상 장치에 관한 기록(2026-11-12)**: 이 자가 진단의 첫 판은 메인 스레드에서 이벤트 루프 없이 스트림을 열었고, eqMac 장치에서 CoreAudio 호출이 돌아오지 않아 10분 뒤 강제 종료했습니다.
그 뒤로 eqMac 장치는 속성 변경(샘플레이트 전환)에는 응답하지만 **새 스트림 시작이 끝나지 않는 상태**입니다(내장 스피커는 정상). 도구는 앱처럼 메인 루프를 돌리도록 고쳤습니다.
eqMac 드라이버 쪽 상태로 보이며 재부팅이나 coreaudiod 재시작으로 풀릴 것으로 예상하지만 확인하지 못했습니다.

**응답하지 않는 장치에서의 앱 동작(🖥, 같은 날)**: 위 상태의 eqMac을 출력 장치로 두고 앱에서 재생을 시작했습니다. 드라이버 호출이 돌아오지 않아 재생 스레드가 멈췄고,
- 12초 뒤 알림 줄에 "출력 장치가 응답하지 않아 재생을 제어할 수 없습니다. 장치 연결을 확인하고, 계속되면 OnEum을 다시 시작하세요."가 표시됐습니다(상태 덤프와 로그로 확인).
- 종료(⌘Q)는 재생 스레드를 8초까지만 기다린 뒤 끝났습니다. 이 처리를 넣기 전에는 종료가 끝나지 않았을 상황입니다.
- 멈춘 호출 자체를 되살릴 방법은 없습니다. 화면은 계속 동작하지만 재생은 앱을 다시 시작해야 합니다.

아직 확인하지 못한 것(⏳):
- **정수 포맷을 가진 실제 USB DAC**: 비트 깊이 전환(16 → 24/32비트)은 선택 규칙만 단위 테스트했습니다. 이 Mac의 두 장치는 32비트 부동소수점 포맷 하나뿐이라 실제 전환이 일어나지 않았습니다.
- 전환에 시간이 걸리거나 릴레이가 붙는 DAC에서의 곡 사이 틈, 전환 직후 첫 소리가 잘리는지 여부.
- 독점 중 다른 출력 장치가 여러 개일 때 macOS가 다른 앱의 소리를 어디로 보내는지, Bluetooth·AirPlay·HDMI 장치.
- 메모리 재생의 실제 효과(잠든 외장 드라이브, 느린 네트워크 폴더). 자동 테스트는 "메모리에 올라간 곡은 파일이 비워져도 끝까지 재생된다"까지 확인합니다.
- 옵션을 켠 채로의 장시간 연속 재생(위 "장시간 재생"은 옵션이 없던 때의 측정입니다).
- 사람 귀로 듣는 확인. 위 확인은 모두 앱 볼륨 0에서 상태와 로그로 했습니다.

## 알려진 문제
- 한 앨범의 파일이 여러 폴더에 흩어져 있고 일부에만 "앨범 아티스트" 태그가 있으면 앨범이 나뉘어 보일 수 있습니다(같은 폴더 안에서는 합쳐 보여 줍니다).
- 음량 분석에서 읽지 못한 곡은 표시해 두지 않으므로, 분석을 다시 시작하면 그 곡의 앨범을 다시 읽습니다(시간만 듭니다).
- 음량 분석이 앨범 하나를 기록할 때마다 목록이 다시 만들어집니다. 5만 곡 라이브러리에서 분석 중 가장 긴 프레임은 2.7ms였습니다(아래 "5만 곡 규모").
- 손상된 `settings.json`을 옆으로 치울 때 이전에 치워 둔 `settings.json.corrupt`가 있으면 덮어씁니다.
- 뒤가 0으로 채워진 수 GB짜리 MP4·MP3를 재생하려 하면 디코더가 파일을 끝까지 훑느라 그만큼 시간이 걸립니다(10GB에 13~21초). 재생은 멈춤 감시가 다음 곡으로 넘깁니다.
- 다채널(5.1/7.1) 파일은 스테레오로 다운믹스합니다.
- 창이 가려져 있으면 macOS가 화면 갱신을 멈춥니다(재생·미디어 키·Now Playing은 영향 없음).
- Finder가 `.opus` 파일에도 OnEum을 제안합니다(macOS가 Ogg와 같은 형식으로 분류). 열면 재생할 수 없다는 안내가 나옵니다.
- 음악 폴더 안의 곡 파일을 **전부** 지우면 그 곡들은 목록에서 사라지지 않고 "사용할 수 없음"으로 남습니다. 폴더가 비워진 것과 드라이브가 잠깐 빠진 것을 구별할 수 없어, 지우지 않는 쪽을 택했습니다. 설정 → 라이브러리에서 그 폴더를 제거하면 정리됩니다(일부만 지운 경우는 평소처럼 목록에서 빠집니다).
- 스캔할 때 내장 이미지를 파일마다 읽으므로, 큰 표지가 들어 있는 대규모 라이브러리를 느린 저장장치에서 처음 스캔하면 시간이 걸릴 수 있습니다.

## 앱 구동 검증
화면 녹화 권한 없이 실제 앱을 확인하기 위한 개발용 통로입니다. `ONEUM_SCRIPT`가 설정된 경우에만 동작합니다(`src/ui/automation.rs`).

```bash
scripts/dev/gen-test-library.sh /tmp/oneum-music
```
```bash
scripts/dev/run.sh /tmp/oneum-profile
```
```bash
scripts/dev/ui.sh /tmp/oneum-profile 'open /tmp/oneum-music' 'wait 2000' 'dclick 300 93' 'wait 1500' 'dump state.json' 'shot shot.png'
```

스모크 테스트(새 프로필 + 합성 라이브러리로 앱을 띄워 109개 항목을 자동 확인, 무음. `scripts/dev/run.sh`가 검증 채널이 든 빌드(`--features automation`)를 만듭니다. 화면이 잠겨 있거나 꺼져 있으면 "창이 돌아온 뒤 다시 그려짐"에서 멈춥니다):
```bash
scripts/dev/smoke.sh
```
첫 실행 → 폴더 추가 → 한글·초성·다중 단어 검색 → 더블클릭 재생 → Space → 다음/이전/탐색 → 셔플·반복 → 앨범·아티스트 보기 → 즐겨찾기 → 대기열 패널 → ⇧화살표 범위 선택 → 검색 칸 Return이 재생을 건드리지 않음 → 곡 메뉴(다음에 재생) → 대기열 키보드(선택·삭제) → 앨범 표지 재생 버튼 → 선택으로 플레이리스트 만들기 → Delete와 실행 취소 → 음소거 → 글자로 곡 찾기 → 남은 시간 전환 → 곡을 플레이리스트·대기열 버튼으로 끌어다 놓기 → 플레이리스트 안에서 끌어 순서 바꾸기 → 파일 메뉴의 플레이리스트 이름 변경·삭제 → 설정 창(탭 전환, 메모리 재생 스위치, 음량 보정 모드, 포맷 열 스위치, Esc·바깥 클릭으로 닫기) → 사용 안내 창 열기·닫기 → 창을 숨긴 채 파일 열기 → VU 미터(−15dBFS 신호가 −7 VU, 일시정지하면 바늘이 내려옴)와 스펙트럼(880Hz 신호의 대역) → 종료 후 재실행 복원까지 확인합니다. 2026-11-12 기준 디버그·릴리스 빌드 모두 통과.

- `menu ID`는 메뉴 막대 명령을 앱 안에서 직접 실행합니다(메뉴 항목을 누른 뒤의 처리 경로). 메뉴 막대에 항목이 실제로 보이고 단축키가 동작하는지는 사람이 확인해야 합니다(⏳).

- `click/dclick/rclick/drag/scroll/key/text`는 egui 입력 이벤트로 들어가므로 실제 마우스·키보드와 같은 경로를 탑니다.
- `oskey`는 OS 키 이벤트를 앱 이벤트 큐에 넣어 메뉴 단축키·응답 체인·입력기를 거칩니다(앱이 활성 상태여야 합니다). `menukey`는 같은 키 이벤트를 메뉴 막대에 직접 넘깁니다(백그라운드에서도 동작).
- `dump`는 상태(JSON), `shot`은 앱이 그린 화면(PNG)을 프로필 폴더에 씁니다.
- 창이 다른 창에 가려져 있으면 화면을 그리지 않으므로 `shot`이 끝나지 않고 더블클릭이 선택으로만 처리될 수 있습니다. 먼저 `activate`(또는 `front`)를 보내세요.
- 출력 장치를 건드리는 확인은 가상 장치로 하면 스피커에 영향을 주지 않습니다: 프로필의 `data/settings.json`에 `"output_device"`(예: `"coreaudio:EQMDevice"`)와 `"output"` 옵션을 적어 두고 실행합니다. 장치 id는 `oneum-libtool audio-devices`로 봅니다.
- 프로필은 `ONEUM_DATA_DIR`로 분리되어 실제 사용자 데이터에 닿지 않습니다. 기본으로 미디어 세션을 끄고(`ONEUM_MEDIA=1`로 켬) 다른 앱의 미디어 키를 가로채지 않습니다.
- 시스템 Now Playing 확인: `swift scripts/dev/nowplaying-probe.swift [pid 명령번호]` (비공개 MediaRemote API를 쓰는 진단 도구이며 앱에는 포함되지 않습니다).
