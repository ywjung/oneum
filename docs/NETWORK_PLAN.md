# 네트워크 재생(DLNA 서버) 계획

상태: 1~4단계와 6단계를 진행했다(2026-11-15). **가짜 서버로만 확인했고, 실제 DLNA 서버로는 확인하지 않았다**(5단계는 검증 대기).
작성 2026-11-15 · 계획 기준: `main`(커밋 cd64a4b) · 작업 브랜치 `feature/network` · 확인 범위는 [TESTING.md](TESTING.md)의 "네트워크의 미디어 서버"

## 진행 결과 (2026-11-15)

9절의 네 가지는 답을 받지 못해 계획의 기본값으로 진행했다: 1차 범위 그대로, 실제 서버 없이, 시험용 서버는 내려받지 않고(가짜 서버만), iPhone은 주소로 추가를 기본 길로.

| 단계 | 결과 |
|---|---|
| 1 통신 | `net::http`·`xml`·`ssdp`·`upnp`. 새 라이브러리 없음. 테스트 안에서 뜨는 가짜 서버(`tests/net_support`)로 통신 테스트 58개(망가진·악의적인 답, 무작위 바이트 포함)와 단위 테스트 26개 |
| 2 재생 | 서버의 곡을 받는 대로 메모리에 올려 재생(`audio::remote`, `audio::source`의 `Origin`). 7개 형식이 파일 재생과 샘플 단위로 같음(메모리·흘려 받기, 탐색, 부분 요청을 받지 않는 서버), 곡 사이 gapless, 사라진 서버의 곡 건너뛰기, 다시 시작 후 대기열 복원 |
| 3·4 화면 | 데스크톱 사이드바와 폰 보관함에 "네트워크". 서버 목록(찾은 것·추가한 것), 주소로 추가, 폴더 둘러보기, 재생·다음에 재생·대기열에 추가. 권한 설명(Mac·iPhone), Android `INTERNET` 권한 |
| 5 실제 서버 | **하지 않음.** 실제 DLNA 서버가 없었다 |
| 6 문서 | PRD, ARCHITECTURE, UX, 사용 안내 6개(Windows 안내는 Mac 안내에서 만들어진다), TESTING, STATUS, CHANGELOG, README |

계획과 달라진 것:
- **대기열 저장**: `queue.track_id`가 `tracks`를 가리키는 외래 키라 음수 번호를 넣을 수 없었다. 그 표는 그대로 두고 서버 곡의 대기열 항목은 `remote_queue` 표에 같은 위치 번호로 둔다. 읽을 때 둘을 위치 순으로 합친다.
- **주소로 추가**: 숫자 주소만 넣어도 되게, 그 호스트의 1900번 포트에 직접 묻는다. 네트워크 전체에 묻는 것이 아니므로 iPhone의 멀티캐스트 제약을 받지 않는다(실제 iPhone에서는 확인하지 않음).
- **AAC**: 지연·패딩 정보를 디코더가 파일을 한 번 더 열어 읽고 있었다. 서버의 곡은 메모리에 올라온 바이트(없으면 따로 맺은 연결)에서 읽는다. 이것이 빠지면 서버의 AAC만 gapless가 깨졌다(테스트가 찾음).
- **메모리 재생**: 서버의 곡은 설정과 무관하게 받는 대로 메모리에 올린다(상한 안에서). 다음 곡이 서버의 곡이면 미리 연결해 올린다.
- **음량 보정**: 넣지 않았다. 서버의 곡에는 태그도 측정값도 없이 재생한다.
- **Android의 멀티캐스트 잠금**: 넣지 않았다. 찾기의 답은 앱의 소켓으로 직접 오므로 필요 없다고 봤으나, 실제 기기에서 찾기가 되는지는 확인하지 못했다.
- **폴더 전체 재생**은 그 폴더 바로 아래의 곡만이다(하위 폴더는 들어가서 재생).

확인하지 못한 것: 실제 DLNA 서버(Synology·miniDLNA 등)와의 호환, 실제 네트워크에서 서버 자동 찾기(테스트는 이 컴퓨터 안에서만 통신), 실제 iPhone·Android 기기, Windows 실행, Wi-Fi가 느릴 때의 끊김, 1GB가 넘는 파일(DSD).

사용자가 "네트워크 플레이어 기능을 추가해 달라"고 했고, 그 뜻을 물어 **DLNA 서버의 음악 듣기**로, 진행은 **계획부터**로 정했다.
지금도 Finder·탐색기에 연결한 NAS 공유 폴더는 음악 폴더로 추가해 들을 수 있다. 이 계획은 그와 별개로, 공유 폴더를 연결하지 않고 같은 네트워크의 미디어 서버(NAS의 DLNA/UPnP 서버 등)를 찾아 둘러보고 재생하는 기능이다.

## 1. 결론

- **할 수 있다.** 필요한 통신은 셋이다: 서버 찾기(SSDP, UDP), 서버의 목록 읽기(UPnP ContentDirectory의 `Browse`, HTTP로 주고받는 XML), 음악 받기(HTTP, 범위 요청). 모두 암호화 없는 HTTP라 표준 라이브러리의 소켓으로 직접 구현할 수 있고, **새 라이브러리를 내려받지 않아도 된다**(XML은 Apple Music 가져오기의 해석기 방식을 따른다).
- 디코더·리샘플러·출력은 그대로 쓴다. 바뀌는 것은 "곡이 어디에 있는가"다: 지금은 파일 경로뿐인데, HTTP 주소가 하나 더 생긴다.
- 네트워크 곡은 **보관함에 넣지 않는다.** 서버를 통째로 스캔하지 않고, 서버가 보여 주는 폴더·앨범을 그때그때 둘러보고 재생한다(1차). 재생한 곡은 대기열과 세션에 남는다.
- 가장 큰 불확실성 둘: 서버마다 다른 동작(실제 서버로만 확인된다), iPhone의 서버 자동 찾기(아래 4절).

## 2. 범위

**1차에 넣는 것**
- 서버 찾기(자동)와 **주소로 직접 추가**, 추가한 서버 기억하기.
- 서버의 폴더·앨범·아티스트 목록을 서버가 주는 구조 그대로 둘러보기(긴 목록은 나눠서 읽기).
- 재생, 다음에 재생, 대기열에 추가(곡 하나, 폴더 전체). 이어지는 곡 사이의 gapless, 탐색, 다시 시작할 때 대기열 복원.
- 표지(서버가 주는 그림), 제목·아티스트·앨범·길이·형식, 곡 정보.
- 서버가 원본 파일을 주는 형식: FLAC, WAV, AIFF, ALAC·AAC(MP4), MP3, Ogg Vorbis, DSF·DFF. 서버가 여러 형식을 내놓으면 원본(무손실)을 고른다.
- 메모리 재생(받는 대로 메모리에 올려, 도중에 네트워크가 끊겨도 그 곡은 끝까지), 헤드폰 보정·이퀄라이저 등 소리 처리 전부, 곡의 샘플레이트로 출력(서버가 샘플레이트를 알려 줄 때).

**1차에 넣지 않는 것(2차 후보)**
- 네트워크 곡의 즐겨찾기·플레이리스트·재생 횟수·통계·다시 듣기, 보관함 검색에 섞기, 서버 안 검색(서버의 `Search`).
- 음량 보정: 파일의 ReplayGain 태그는 디코더가 열 때 읽을 수 있으면 쓰고, 없으면 보정 없이 재생한다(분석은 하지 않음). 가능 여부는 구현하며 확인한다.
- 가사(옆의 .lrc 파일), 파일 검사, "Finder에서 보기".
- OnEum을 렌더러로 쓰기, 네트워크 스피커로 보내기, 계정이 필요한 서버(Subsonic 등), 인터넷 라디오, 집 밖에서 접속. (이번에 고르지 않은 것들이다.)

## 3. 구조

| 부분 | 내용 |
|---|---|
| `net::http` (새로) | HTTP/1.1 클라이언트: GET(범위 요청), POST(SOAP), Content-Length와 chunked, 리다이렉트(3번까지), 연결·읽기 시간 제한, 크기 상한. TLS 없음(같은 네트워크의 `http://`만) |
| `net::ssdp` (새로) | `M-SEARCH`(MediaServer:1)를 보내고 답의 `LOCATION`을 모은다. 찾는 동안만 UDP 소켓을 연다. 앱이 여는 포트는 없다(서버의 알림 구독은 하지 않음) |
| `net::upnp` (새로) | 장치 설명(이름, UDN, ContentDirectory의 주소) 읽기, `Browse` 호출, DIDL-Lite 해석(폴더·곡, `res`의 주소·형식·길이·샘플레이트·비트, 표지 주소) |
| 곡의 위치 | `PlayableTrack.path: PathBuf`를 "파일 경로 또는 HTTP 주소"로 넓힌다. 디코더의 입력(`MediaSource`)에 HTTP 소스를 더한다: 범위 요청으로 탐색, 길이는 Content-Length |
| 메모리 재생 | `audio::source`의 "받는 대로 메모리에, 아직 안 받은 곳은 원본에서"를 파일뿐 아니라 HTTP에도 쓰게 일반화 |
| 네트워크 곡의 기록 | 대기열과 세션은 곡 번호(`TrackId = i64`)로 움직인다. 네트워크 곡은 보관함의 `tracks`가 아닌 별도 표(`remote_tracks`: 서버, 서버 안의 ID, 주소, 제목·아티스트·앨범·길이·형식, 표지 주소)에 두고 **음수 번호**를 준다. 플레이어의 호스트(`LibraryHost::track`)와 화면의 곡 조회가 부호로 갈라 찾는다. 스키마 버전을 올린다(이전 버전 DB에서 올라오는 마이그레이션과 테스트 포함) |
| 서버 목록 | 설정 파일에 사용자가 추가한 서버(주소, 이름). 자동으로 찾은 서버는 기억하지 않는다 |
| 표지 | 서버의 그림을 받아 기존 표지 캐시에 넣는다(주소로 키를 만듦, 크기 상한) |
| 화면 | 5절 |

곡 번호를 음수로 쓰는 방식은 대기열·세션·화면 곳곳이 "번호 > 0"이나 "보관함에 있음"을 가정하는지 전부 확인해야 한다. 가정이 많으면 `tracks` 표에 서버용 뿌리(root)를 두는 방식으로 바꾼다. 이 판단이 2단계의 첫 일이다.

## 4. 플랫폼별로 필요한 것

| 플랫폼 | 필요한 것 | 확인할 수 있는 범위 |
|---|---|---|
| macOS | Info.plist에 로컬 네트워크 사용 설명(처음 쓸 때 시스템이 허용을 묻는다) | 이 Mac에서 직접 |
| Windows | 추가 설정 없음(답을 받는 UDP가 방화벽에 막히는지 확인 필요) | **실행 미검증**(지금까지와 같음) |
| iPhone | Info.plist에 로컬 네트워크 사용 설명. **자동 찾기는 실제 기기에서 안 될 가능성이 높다**: iOS는 멀티캐스트를 보내는 데 Apple이 따로 승인하는 권한(multicast entitlement)을 요구하고, 개인 서명으로는 받을 수 없는 것으로 안다(확인 필요). 그래서 **주소로 직접 추가**를 기본 길로 둔다 | 시뮬레이터(자동 찾기 제약이 없음), 실제 기기는 사용자가 설치할 때 |
| Android | `INTERNET` 권한, 찾는 동안 Wi-Fi 멀티캐스트 잠금(`CHANGE_WIFI_MULTICAST_STATE`) | 에뮬레이터(호스트의 서버는 `10.0.2.2`로), 실제 기기는 **검증 대기** |

폰에서 화면 밖 재생은 지금의 오디오 세션·재생 서비스가 그대로 맡는다. 네트워크가 끊기면 받아 둔 만큼(메모리 재생이면 곡 끝까지) 재생하고, 다음 곡을 못 받으면 "파일을 찾을 수 없음"과 같은 길(건너뛰기와 알림)로 간다.

## 5. 화면

- **데스크톱**: 사이드바에 "네트워크" 묶음(찾은 서버와 추가한 서버). 서버를 고르면 본문에 그 서버의 폴더 목록, 폴더를 열면 하위 폴더와 곡. 위에 경로(뒤로 가기)와 "서버 추가…", "다시 찾기". 곡은 두 번 눌러 재생(그 폴더의 곡이 대기열로), 메뉴에 재생·다음에 재생·대기열에 추가·곡 정보.
- **폰**: 보관함 탭에 "네트워크" 줄 → 서버 목록(찾은 것, 추가한 것, "주소로 추가") → 폴더 화면(기존 목록 화면과 같은 모습, ⋯ 메뉴).
- 재생 중 화면·대기열·알림·잠금 화면에는 보관함 곡과 같이 나온다. 네트워크 곡에 없는 기능(즐겨찾기 등)은 메뉴에서 빼거나 흐리게 한다.
- 한국어·영어 문구, 사용 안내 네 가지(macOS·Windows·iPhone·Android)의 한·영에 절을 더한다.

## 6. 신뢰할 수 없는 입력과 사생활

네트워크에서 오는 것은 전부 신뢰하지 않는다(지금까지의 손상·적대적 입력 점검과 같은 기준).
- 크기와 시간의 상한: 장치 설명 1MB, `Browse` 답 8MB, 한 번에 200개씩, 표지 16MB, 연결 3초·읽기 10초, 리다이렉트 3번. XML은 깊이 상한, 외부 엔티티·DTD 무시.
- 주소는 `http://`만 따른다. 서버가 준 주소가 다른 호스트를 가리켜도 받기는 하되(서버가 다른 장치의 음악을 중계하는 경우가 있음) 같은 상한을 적용한다. 자격 증명을 보내지 않는다.
- 음악 데이터는 파일과 같은 디코더 한도(읽기 예산, 해석 비용 상한)를 그대로 받는다.
- **"기본은 오프라인"을 지킨다**: 네트워크 화면을 열거나 서버를 추가하기 전에는 아무 통신도 하지 않는다. 그 뒤에도 통신은 같은 네트워크의 그 서버와만 한다. 수집·계정 없음. PRD의 "범위 밖"에서 이 기능을 빼고 원칙의 문장을 고친다.

## 7. 단계

| 단계 | 내용 | 끝났다는 기준 |
|---|---|---|
| 1 통신 | `net::http`, `net::ssdp`, `net::upnp`와 시험용 가짜 서버(테스트 안에서 뜨는 것) | 찾기·설명·Browse·DIDL 해석 테스트, 망가진·악의적인 답(끝없는 답, 거대한 길이, 깊은 XML, 느린 서버) 테스트 |
| 2 재생 | 곡의 위치 넓히기, HTTP 소스, 메모리 재생 일반화, `remote_tracks`와 세션 | 가짜 서버의 FLAC·MP3·MP4를 재생한 샘플이 파일 재생과 같음, 탐색, gapless, 도중에 서버가 사라짐, 다시 시작 후 복원 |
| 3 데스크톱 화면 | 사이드바, 폴더 목록, 서버 추가, 표지, 메뉴, 문구 | macOS 스모크 테스트에 절 추가(가짜 서버를 주소로 추가 → 둘러보기 → 재생, 무음) |
| 4 폰 화면 | 보관함 → 네트워크, 권한 설명, Android 권한·멀티캐스트 잠금 | iPhone 시뮬레이터와 Android 에뮬레이터 스모크 테스트에 절 추가 |
| 5 실제 서버 | 사용자의 서버(또는 허락 시 이 Mac에 설치한 공개 서버)로 확인하고 서버별 차이를 고침 | 그 서버에서 찾기·둘러보기·재생·탐색·표지 |
| 6 문서 | PRD, ARCHITECTURE, UX, 사용 안내 8개, TESTING, STATUS, CHANGELOG, README, 홈페이지 | 안내의 한·영 구성 테스트 통과 |

단계마다 `scripts/check.sh`(포맷, 네 플랫폼 린트, 전체 테스트)를 통과시키고 커밋은 요청하실 때 한다. 재생 확인은 모두 앱 음량 0에서 한다.

## 8. 위험과 확인하지 못할 것

- **서버마다 다른 동작**: 폴더 구조, `res`가 여러 개일 때의 순서, 범위 요청을 받지 않는 서버(탐색 불가 → 처음부터만 재생), 변환(LPCM)만 내놓는 서버, 한글 인코딩, 긴 목록. 가짜 서버는 내가 아는 만큼만 흉내 내므로, **실제 서버 하나 이상으로 확인하기 전에는 "된다"고 적지 않는다.**
- **iPhone 자동 찾기**: 4절. 주소 추가로 쓸 수 있지만, 서버의 주소가 바뀌면(DHCP) 다시 넣어야 한다.
- **Wi-Fi 품질**: 고해상도·DSD 파일은 크다. 메모리 재생이 받는 대로 올리지만, 폰은 메모리 상한(256MB)을 넘는 파일을 흘려 받으며 재생하므로 끊김이 날 수 있다.
- **Windows, 실제 Android 기기**: 지금까지와 같이 실행을 확인하지 못한다.
- 곡 번호를 음수로 쓰는 방식이 맞지 않으면 3절의 대안으로 바꾸며, 그만큼 2단계가 커진다.

## 9. 시작 전에 정해 주실 것

1. **확인에 쓸 실제 DLNA 서버가 있습니까?** (예: Synology·QNAP의 미디어 서버, MinimServer, miniDLNA, Plex) 있으면 종류와, 5단계에서 그 서버로 직접 확인해 주실 수 있는지.
2. **시험용 서버 설치 허락**: 실제 서버가 없거나 미리 확인해 두려면 이 Mac에 공개 DLNA 서버 하나(예: miniDLNA)를 내려받아 시험용 폴더만 보여 주게 띄운다. 내려받기이므로 허락이 필요하다. 허락하지 않으면 가짜 서버만으로 진행하고 실제 서버는 검증 대기로 적는다.
3. **1차 범위**: 2절대로(둘러보기와 재생만, 즐겨찾기·플레이리스트·검색은 2차) 좋은지.
4. **iPhone**: 자동 찾기가 안 되면 주소 직접 추가만으로 내도 되는지.
