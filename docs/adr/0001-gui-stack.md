# ADR 0001 — GUI 스택: egui/eframe 유지

- 상태: 확정 (2026-11-11)
- 검증 환경: macOS 27.2.1, Apple M4, Rust 1.99.1, eframe/egui 0.37.0, winit 0.30.13

## 배경
한글 입력이나 접근성에 중대한 결함이 있으면 UI를 대량 구현하기 전에 스택을 바꿔야 한다.
`.app` 번들로 만든 스파이크 앱에서 아래를 실제로 실행해 확인했다.

## 검증 결과
| 항목 | 방법 | 결과 |
|---|---|---|
| 창 + 네이티브 메뉴 | muda 0.21로 앱/파일/편집/윈도우 메뉴 구성, 메뉴 항목 실행 | 이벤트 수신 확인 |
| 한글 조합 입력 | 두벌식 입력 소스 선택 후 CGEvent 기반 키 이벤트를 앱 이벤트 큐에 게시 (`gksrmf dmadkr`) | `한글 음악`, 조합 중 백스페이스 `음아`, 입력 소스 전환 시 확정 모두 정상 |
| 복사·붙여넣기 | ⌘A → ⌘C → → → ⌘V | 메뉴 없음: 정상 / 네이티브 편집 메뉴 있음: **실패** → 브리지 적용 후 정상 |
| 접근성 트리 | macOS 접근성 API로 조회 | AXTextField, AXButton, AXCheckBox(레이블 포함) 노출 |
| 5만 행 표 | `egui_extras::TableBuilder::body().rows()` | 보이는 행만 그림, 스크롤·선택 정상 |
| 한글 글꼴 | eframe `system_fonts` 기능 | 별도 글꼴 번들 없이 한글 표시 |

## 발견한 문제와 대응
1. **편집 메뉴가 ⌘C/⌘V를 삼킴.** 메뉴의 `copy:`/`paste:` 액션은 응답 체인의 첫 응답자에게 가는데
   winit 뷰가 구현하지 않아 키 입력이 사라진다. → `platform/macos/responder.rs`가 런타임에
   `WinitView`에 해당 메서드를 추가해 egui 이벤트로 전달한다. 파일 패널 등 네이티브 텍스트 필드는
   같은 셀렉터를 스스로 처리하므로 영향이 없다.
2. **입력 소스 전환 직후 약 1초간 조합되지 않음.** 프로그램으로 입력 소스를 바꾼 직후에만 나타났고
   3초 대기 후에는 첫 글자부터 정상이었다. 입력기 활성화 지연으로 판단한다(실사용 경로 아님).
3. **아이콘 버튼의 접근성 이름.** 글리프만 있는 버튼은 이름이 글리프가 된다. → 모든 아이콘 버튼에
   `WidgetInfo`로 이름과 툴팁을 지정한다.

## 결정
egui + eframe(wgpu/Metal) + egui_extras 표 + AccessKit + muda 메뉴를 사용한다.
objc2-app-kit 기반 네이티브 UI는 검토 대상에서 제외한다(중대한 결함 없음, 구현 비용 큼).

## 남은 위험
- VoiceOver 음성 출력 자체는 사람이 확인해야 한다(TESTING.md의 수동 검증 항목).
- winit 클래스에 메서드를 추가하는 방식은 winit 내부 클래스 이름에 의존한다. 클래스가 없으면
  설치 함수가 `false`를 반환하고 로그를 남긴다(편집 단축키만 영향).
